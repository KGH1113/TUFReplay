# 웹 카메라 프리뷰의 간헐적 저속 현상 조사

2026-10-21 한국 시간 기준으로 `Player.log`, `Player-prev.log`, 각 실행의 handshake가 가리키는 native helper 로그와 현재 `dev` 브랜치의 프리뷰 경로를 확인했다. 사용자가 알려 준 얼불춤 업데이트 충돌은 이번 조사 대상에서 제외했다. 사용자는 웹 카메라 창을 보고 있을 때와 게임에서 웹으로 돌아올 때 모두 프리뷰가 느려진다고 확인했다.

## 확인된 사실

가장 최근 실행의 안정된 게임 플레이 구간 8개, 약 40초의 가중 평균은 **238.44 FPS**였다. 각 구간은 **236.94–239.00 FPS**였다. 카메라 수신은 약 **30 FPS**, 초기 프리뷰 활성화 구간을 제외한 공유 프리뷰 발행은 약 **24–29 FPS**였다. native worker가 긴 시간 변환 중이거나 pending frame을 계속 교체하는 모습은 없었다. 이 실행에서 게임 FPS가 지속적으로 떨어지는 현상은 확인되지 않았다.

반면 직전 실행에는 **카메라 수신 자체가 멈춘 구간**이 있었다. iPhone 13 카메라에서 받은 총 프레임 수와 공유 프리뷰 발행 수가 모두 151에서 멈췄다.

| 시각(KST) | 누적 수신 | 구간 수신 FPS | 마지막 수신 후 경과 | 프리뷰 발행 누적 | 프리뷰 요청 |
| --- | ---: | ---: | ---: | ---: | --- |
| 03:03:22 | 35 | 31.05 | 약 0초 | 34 | 있음 |
| 03:03:27 | 151 | 22.78 | 1.23초 | 151 | 있음 |
| 03:03:32 | 151 | 0 | 6.23초 | 151 | 없음 |
| 03:03:42 | 151 | 0 | 16.23초 | 151 | 있음 |
| 03:03:57 | 151 | 0 | 31.23초 | 151 | 있음 |

그동안 `sessionRunning: true`, 장치 `connected: true`, `suspended: false`였고, runtime error·interruption·dropped frame 기록은 없었다. worker는 `pending: false`, `inFlightAgeSeconds: null`이며 마지막 변환은 약 2.51ms에 완료돼 있었다. 녹화 중이 아닌 `armed` 상태였다. 종료 명령 직전 마지막 수신 경과 시간은 약 35.39초였다.

수신 카운터는 `WebcamCaptureService.captureOutput(...didOutput...)`의 첫 부분에서 증가한다. health timer도 그 callback queue에서 계속 실행되고 있었다. 따라서 이 정지 구간은 웹 이미지 표시가 느린 것만으로 설명할 수 없고, 프리뷰 변환 worker의 작업 적체나 해당 callback queue의 지속적인 교착으로도 설명하기 어렵다. **새 캡처 프레임이 callback으로 들어오지 않는 상태**가 확인된 것이다. 원인이 장치·연결·AVFoundation 세션·우리의 세션 관리 중 어디에 있는지는 아직 확정할 수 없다. 요청을 다시 보낸 구간에서도 수신이 회복되지 않았으므로 단순한 프리뷰 수요 중단만을 원인으로 볼 수 없다.

증거 위치:

- `~/Library/Logs/TUFReplay/camera-helper-2026-10-20T18-03-16Z-48079-4C4B5829.jsonl`: 21–28행의 `capture.health`, 30행의 종료 직전 상태.
- `~/Library/Logs/TUFReplay/camera-helper-2026-10-20T18-04-11Z-51095-10450424.jsonl`: 가장 최근 실행의 정상적인 수신·발행 상태.
- `~/Library/Logs/7th Beat Games/A Dance of Fire and Ice/Player.log`: 5109–56520행 사이의 안정된 플레이 `render.performance` 8개 구간.

## 웹 경로에서 확인한 별도의 지연 요인

현재 웹 프리뷰는 원래 **최대 약 8 FPS**로 제한돼 있다. 카메라의 30 FPS나 게임의 240 FPS와 같은 목표가 아니다.

`web/src/state/webcam/game-camera-session.ts`는 요청 하나를 완료한 **뒤에** 125ms를 기다린다. 이 요청에는 IPC 응답과 HTTP 이미지 다운로드가 포함된다. 따라서 실제 전달 간격은 `요청·다운로드 시간 + 125ms + 타이머 스케줄 지연`이다. 이미지 decode·React 반영·화면 표시는 그 이후에 일어나며 현재 루프는 표시 완료를 측정하지 않는다. 예를 들어 요청·다운로드에 500ms가 걸리면 이론적인 상한도 약 1.6 FPS로 내려간다. 이는 코드에서 확인되는 특성이며, 이번 실행에서 실제로 500ms가 걸렸다는 뜻은 아니다.

`TUFReplay/Webcam/Ipc/WebcamPreviewIpc.cs`에는 마지막 요청으로부터 1초가 넘으면 재개로 판단해 `ready: false`를 반환하는 분기가 있다. 지속적인 전송 지연이나 스케줄 지연으로 요청 간격이 1초를 넘으면 이 분기가 반복될 수 있다. 또한 재개 시 source freshness 타이머가 다시 시작되므로 간헐적인 요청 사이에서는 정지 감지가 늦어질 수 있다. 이것 역시 이번 저속 현상의 원인으로 실측된 것은 아니다.

서버는 공유 프레임 복사와 BMP 변환을 IPC background context에서 수행한다. 게임 스레드에서 웹 프리뷰 이미지 전체를 변환하는 구조는 아니다. 다만 게임과 같은 프로세스의 작업이므로 모든 간접 부하가 배제됐다는 뜻은 아니다.

## 지금 확정할 수 없는 것

가장 최근 실행의 native 수신과 공유 프리뷰가 정상일 때 실제 웹 표시 FPS가 얼마였는지는 로그에 없다. 현재 두 Player 로그에는 `webcam.preview.read`의 요청 소요 시간, HTTP 전송 시간, 프런트엔드 표시 시간, 프리뷰 오류의 진단 이벤트가 남지 않는다. 따라서 다음을 구분해야 한다.

1. 직전 실행에서 확인된 native 캡처 수신 정지.
2. native 수신이 정상일 때 웹 경로에서 발생했을 가능성이 있는 지연.

두 현상 모두 카메라 프리뷰로 보이지만, 이전의 게임 FPS 저하와 같은 원인이라고 확정할 증거는 없다. 웹을 직접 보는 중에도 발생한다는 사용자 관찰상 백그라운드 탭 제한 하나만으로 전체 현상을 설명하는 것도 부적절하다.

지난번 추가한 엔진 계측은 이번 실행에서 로드됐다(schema 3). 다만 GPU Frame Timing Stats는 게임 빌드에서 비활성화돼 있고 일부 엔진 마커도 제공되지 않는다. 이 실행의 GPU 병목 유무를 실측 GPU 시간으로 판정할 수는 없다.

## 다음 수정에서 확보해야 할 정보

- native: 일정 시간 새 callback이 없는 상태를 별도 stall 이벤트로 전환하고, 회복 시각과 session/device 상태를 함께 기록한다. 프리뷰 재요청과 실제 캡처 재시작을 구분한다. 녹화 중 재시작은 영상·타임라인에 영향을 줄 수 있으므로 복구 정책을 따로 정해야 한다.
- 서버: 프리뷰 요청 간격, 프레임 sequence와 freshness, 복사 성공/실패 사유, 복사·BMP 변환·응답 준비 시간을 구간별로 집계한다.
- 웹: IPC 응답, HTTP 다운로드, 이미지 표시 완료와 실제 표시 FPS를 나누고 page visibility와 함께 집계한다. 원본이 느린지 전송이 느린지 화면 표시가 느린지 구분할 수 있어야 한다.
- 시각과 프레임 식별자로 각 구간을 연결한다. 저속 상태에서 요청을 병렬로 쌓는 방식은 피하고, 읽기 완료 후 고정 대기를 더하는 현재 정책과 재개 판정의 상호작용을 검증한다.

이번에는 로그와 코드의 읽기 조사만 수행했으며 구현 소스는 변경하지 않았다. 빌드·테스트·장치 재시작은 수행하지 않았다.
