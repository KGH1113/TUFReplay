# 오프라인 렌더링용 공통 시간·입력 SDK 설계

작성일: 2026-10-11, Asia/Seoul. 상태: 사용자 선택과 구현 승인을 반영한 설계. 이 문서는 공용 계약을 정의하며 특정 모드의 내부 구조에 의존하지 않는다.

## 목적과 범위

모드는 기존 UI와 애니메이션을 사용하면서 시간·입력을 공용 wrapper에서 읽는다. Renderer는 기록된 입력과 렌더 시각을 제공하고, UI 갱신이 끝난 기존 Unity Canvas를 게임 화면과 함께 캡처한다. 모드가 픽셀 버퍼나 영상 프레임을 만들거나 인코더를 호출할 필요는 없다.

첫 버전은 오프라인 렌더링만 지원한다. 기존의 자동 모드 검색·시간 및 입력 코드 패치에 의존하는 호환 경로는 SDK 연동으로 전환한다. 일반 플레이에서는 모드의 원래 입력과 시간이 작동해야 한다.

SDK의 책임은 시간·키 상태 공급, 렌더 세션 수명주기, 참여 모드 식별과 오류 전달이다. UI 표현, 게임 상태 해석, 내부 카운터 구조와 애니메이션 구현은 각 모드가 맡는다.

## 렌더링의 의미

Renderer는 native input CSV의 이벤트를 시각 순서대로 소비해 현재 눌려 있는 키 집합을 계산한다. 참여 모드는 각 논리 갱신에서 그 상태를 조회한다. 모드가 기존에 상태 변화로 눌림과 뗌을 판단한다면 같은 방식을 사용한다.

한 갱신 구간에 같은 키의 press/release가 모두 들어와 최종 상태가 이전 상태와 같다면, 상태 조회만 하는 모드는 그 입력을 표시하지 않을 수 있다. 이 동작은 허용한다. SDK가 짧은 입력을 강제로 보이게 하거나 카운트·KPS·키 이펙트 알고리즘을 교정하지 않는다.

이 정책은 SDK에 제공하는 키 상태에만 적용한다. 원본 이벤트와 순서는 게임 시뮬레이션, 오디오 등에서 계속 사용하며 기록 자체를 축약하거나 버리지 않는다.

모드는 판정·콤보·진행도처럼 기록에 직접 없는 값을 기존 게임 시뮬레이션에서 읽는다. SDK가 별도의 게임 상태 모델을 만들지는 않는다.

## 시간 계약

UI 애니메이션, KPS 측정, 키 이펙트의 시간은 출력 영상의 경과 시간을 사용한다. 기록 시간과 출력 시간의 pitch 변환은 Renderer의 기존 timeline이 수행한다. SDK는 변환을 다시 하지 않는다. 노래 위치나 게임 판정에 필요한 시간은 기존 게임 상태를 읽는다.

| 값 | 렌더 중 | 렌더 밖 |
| --- | --- | --- |
| UI 경과 시간 | 현재 논리 갱신의 출력 영상 시각 | 해당 API의 원래 값 |
| UI delta | 이번 논리 갱신에서 진행한 시간 | 해당 API의 원래 값 |
| Stopwatch 경과 시간 | 해당 렌더 세션의 가상 watch 상태 | 원래 Stopwatch의 값 |
| 키 눌림 상태 | CSV에서 계산한 현재 상태 | 모드의 원래 입력 backend |

시간과 입력 snapshot은 같은 논리 갱신 번호에 속한다. 모드가 한 번 갱신하는 동안 그 값이 바뀌지 않도록 Renderer가 게시 경계를 관리한다. 렌더 시계는 실제 작업 속도와 관계없이 단조 증가한다. 최초 갱신의 delta는 0으로 정의한다.

현재 시뮬레이션 FPS와 영상 FPS의 관계를 유지한다. 영상 FPS가 높아 같은 캡처 이미지를 반복하는 동안 모드의 시간을 추가로 진행시키지 않는다. UI 갱신을 기다리는 추가 Unity 프레임에서는 시각과 키 상태를 고정하고 delta를 0으로 제공한다. 키 상태 비교와 카운트 처리는 같은 논리 갱신에서 중복 실행하지 않는다.

파일 I/O timeout, 네트워크 timeout, 실제 성능 측정, 작업 취소 deadline은 실제 시계를 유지한다. 프로그램 안의 모든 시간 API를 가상화하지 않는다.

## Wrapper 형태

익숙한 시간·입력 조회 형태를 유지하는 얇은 wrapper를 제공한다. 작업용 API 이름은 `ReplayTime`, `ReplayStopwatch`, `ReplayInput`, `RenderSession`이며 실제 이름과 signature는 첫 포팅에서 확정한다.

- 시간 wrapper는 모드가 사용하는 `Time.unscaledTime`, `Time.unscaledDeltaTime` 등의 조회를 대체한다. Renderer가 없거나 렌더 중이 아니면 원래 Unity 값을 직접 반환한다.
- Stopwatch wrapper는 조회뿐 아니라 `Start`, `Stop`, `Reset`, `Restart`의 상태를 구분한다. 렌더 세션의 가상 누적 상태와 원래 `System.Diagnostics.Stopwatch` 상태를 분리한다. 렌더 중의 조작이 실제 watch를 바꾸지 않는다.
- `ElapsedTicks`와 `Elapsed.Ticks`는 원래 단위를 유지한다. Stopwatch frequency와 TimeSpan tick 단위를 혼동하지 않는다.
- 입력 wrapper는 현재 키 상태를 제공한다. 일반 플레이의 입력 backend가 Unity Input과 다르면 해당 모드의 기존 입력 gateway를 native fallback으로 연결한다. 원래 backend를 Unity Input으로 일괄 교체하지 않는다.
- 렌더 여부와 논리 갱신 번호를 조회할 수 있어, 모드가 실제 입력 차단·중복 갱신 방지·저장 억제를 명확한 경계에서 처리할 수 있게 한다.

단순 getter는 native 경로와 렌더 경로를 선택하는 분기만 거치도록 설계한다. 키 매핑과 snapshot 저장 공간은 세션 준비 때 생성하고 getter에서 할당하지 않는다. 일반 플레이에서 전체 이벤트를 새 큐로 우회시키거나 매번 reflection을 실행하지 않는다. wrapper 도입의 비용이 0이라고 가정하지 않고 실제 경로에서 확인한다.

## 세션과 모드의 책임

각 모드는 이름과 식별자, 세션 시작·종료·제외 처리 callback을 등록한다. 등록은 모드 내부를 발견해 패치하기 위한 장치가 아니라, 모드가 소유한 상태를 안전하게 전환하고 실패한 참여자를 식별하기 위한 계약이다.

세션 시작은 다음을 보장해야 한다.

1. 원래 사용자 설정과 표시 상태를 보존한다.
2. 렌더용 카운터·키 상태·KPS·이펙트를 초기 상태로 준비한다.
3. 실제 입력 listener나 worker가 렌더 상태를 갱신하지 않도록 전환한다.
4. 렌더용 시간·입력과 기존 UI 갱신 경로를 연결한다.

세션 종료·취소·실패는 같은 정리 경로를 사용한다. 실제 입력, 원래 모델과 설정을 복구하고 렌더용 상태를 폐기한다. 시작이 일부만 성공한 경우에도 이미 전환한 자원을 정리할 수 있어야 한다.

카운터·프로필을 저장하는 모드는 임시 렌더 모델이나 명확한 저장 정책을 사용한다. 렌더 때문에 사용자의 누적 카운터나 설정 파일을 덮어쓰지 않는다. 이미 진행 중인 일반 플레이의 저장 작업은 원래 모델을 대상으로 완료되게 한다. SDK가 임의의 전역 singleton이나 사설 필드를 복제하지 않는다.

창 포커스나 편집기 상태 때문에 UI 갱신을 건너뛰는 모드는 렌더 여부를 이용해 해당 gate를 명시적으로 전환한다. 출력 해상도가 필요한 레이아웃에는 렌더 context의 크기를 전달한다. 렌더 밖에서는 원래 포커스·화면 크기 값을 사용한다. SDK가 타 모드의 `Application`, `Screen` 또는 게임 상태 접근을 자동으로 재작성하지 않는다.

## 갱신과 캡처 순서

한 논리 갱신의 순서는 다음과 같다.

1. Renderer가 기존 timeline과 cursor를 사용해 게임과 기록 입력을 진행한다.
2. 해당 시점의 출력 시간·delta·키 상태 snapshot을 게시한다.
3. 참여 모드가 같은 snapshot으로 기존 UI를 갱신한다.
4. 필요한 메인 스레드 UI 반영을 기다린다. 이 동안 snapshot은 고정한다.
5. 기존 Canvas 합성 경로로 캡처하고 영상 출력에 사용한다.

모드가 비동기 계산을 사용하면 렌더용 갱신의 완료 또는 실패를 계약 경계에서 알릴 수 있어야 한다. Renderer가 사설 queue를 조사하거나 게임 스레드에서 worker 완료를 무한정 기다리지 않는다. 일반적인 UI 작업은 메인 스레드의 기존 갱신 함수를 재사용한다.

기존 Canvas 선택·레이어 분리·HUD camera·출력 texture 합성을 유지한다. Canvas를 SDK에서 새로 그리거나 영상 API를 추가하지 않는다. 기존 캡처 조건에 맞는 모드 UI는 그대로 사용하고, 캡처 조건에 맞지 않는 UI는 기존 선택 조건을 기준으로 별도 확인한다.

## 참여 모드 오류

참여 모드의 SDK callback 또는 명시적인 갱신 완료 보고에서 오류가 발생하면 다음 프레임의 출력 전에 렌더를 멈추고 사용자에게 선택을 요청한다. 오류가 난 모드 이름, 상황과 선택 결과를 표시한다.

| 사용자 선택 | 처리 |
| --- | --- |
| 해당 오버레이 제외 후 계속 | 해당 모드의 렌더 갱신과 화면 기여를 이번 job에서 제외하고, 나머지 상태가 유효한 현재 논리 프레임의 UI 반영·캡처를 완료한다. |
| 렌더 취소 | 정상 취소 정리를 수행하고 실제 입력·원래 모드 상태를 복구한다. |

같은 프레임에서 실패한 모드를 자동 재시도하지 않는다. 결정을 기다리는 동안 시계와 입력을 진행하지 않고, 응답은 job·session·decision 식별자로 검증한다.

제외 처리는 소유 UI root를 숨기고 렌더 작업을 중지하는 등 명확한 수명주기 동작이어야 한다. 캡처 경로가 Canvas를 다시 활성화할 수 있으므로 `Canvas.enabled = false`만으로 제외됐다고 가정하지 않는다. 원래 표시 상태 복구는 job 종료 시 수행한다.

SDK가 식별할 수 없는 임의의 Unity 예외를 모두 특정 모드의 오류로 포착한다고 약속하지 않는다. 게임·인코더·레벨 실패는 기존 Renderer 오류 정책을 따른다. 모드 제외 후에도 안전한 캡처가 불가능하면 정상 실패 정리를 수행한다.

## 배포와 저장소

공용 SDK와 Renderer, SDK 검증 코드는 Renderer 모노레포에 둔다. SDK는 독립 프로젝트와 명확한 namespace 경계를 갖는다. 개발 문서와 예제는 특정 모드 이름이나 내부 타입에 의존하지 않는다.

모드 package에는 공용 SDK DLL을 동봉한다. 별도 UMM 의존성 모드를 설치하게 하지 않는다. Renderer와 모드가 같은 assembly identity와 호환 ABI를 참조하도록 관리한다. 개별 모드에서 SDK 소스를 복사하거나 assembly 이름을 바꾸어 별개의 static registry를 만들지 않는다.

첫 대상 framework는 실제 소비 프로젝트와 호환되는 `netstandard2.0`을 기준으로 검토한다. 필요한 Unity wrapper를 포함하되 배포에 필요한 공용 DLL 수는 최소화한다. 최종 framework와 참조는 실제 모드 빌드로 확정한다.

각 모드 폴더에 DLL 복사본이 있어도 실제 UMM/Mono에서 같은 공급자 상태를 공유하는지는 런타임 검증이 필요하다. assembly 이름이 같다는 이유만으로 보장됐다고 취급하지 않는다. 첫 연동 전에 로드 순서, 중복 복사본, 호환·비호환 버전, Renderer 미설치 조건을 검증하고 실패 조건을 명시한다.

## 완료 기준

- Renderer가 없을 때 native 시간·입력이 작동하고 모드의 일반 플레이 기능이 유지된다.
- 느린·빠른 실제 렌더 속도에서 UI 시간과 입력이 같은 출력 시각을 사용한다.
- 프레임 사이의 짧은 press/release는 모드의 상태 조회 방식에 따라 처리된다.
- 추가 UI 대기 프레임과 반복 영상 프레임에서 카운트와 애니메이션이 중복 진행하지 않는다.
- 세션 시작·종료·취소·모드 제외 후 실제 입력과 기존 상태가 복구된다.
- 렌더 전후 사용자 카운터·프로필 파일이 렌더 때문에 변하지 않는다.
- DLL 동봉 상태의 실제 UMM 로드와 공통 공급자 공유를 확인한다.
- 기존 Canvas 합성과 현재 FPS 정책이 유지된다.
- macOS에서 실제 게임 렌더를 검증하고 Windows 검증은 후속 필수 단계로 남긴다.

사용자가 구현 시작을 승인했다. 구현과 실제 게임 검증 결과는 별도의 작업 결과 문서에 기록한다. impl-dmnote는 변경 범위에서 제외한다.
