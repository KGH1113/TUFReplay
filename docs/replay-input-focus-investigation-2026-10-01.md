# 리플레이 키뷰어 눌림 표시와 포커스 조사

## 현재 상태

키뷰어 자체는 보이지만, 리플레이 입력의 눌림 표시가 보이지 않는 문제를 조사 중이다.
포커스 문제는 가능한 원인이며 아직 확정하지 않았다. 이번 변경은 원인 확인을 위한
로그 추가다. 눌림 표시 문제의 수정 완료를 의미하지 않는다.

사용자가 제안한 포커스 가설을 확인하기 위해 게임 창으로 돌아왔을 때 눌림 표시가
회복되는지 직접 재현하려고 했다. 게임은 꺼져 있었고 computer-use 접근이 승인되지
않아 실행되지 않았다. 이번 검증에서도 게임 실행과 모드 설치는 수행하지 않았다.

## 확인한 범위

- 카메라 작업 시작점 `5db4720d`와 현재 `f92367b8`의 macOS 입력 전송 코드와
  포커스 검사 코드는 같다. 카메라 작업의 미커밋 변경도 이 두 경로를 바꾸지 않았다.
- 이 두 커밋 사이의 리플레이 네이티브 입력 변경은
  `ReplayInputScheduler`의 탐색 체크포인트 최적화다.
- macOS 카메라 헬퍼가 명시적으로 앱을 활성화하는 시점은 최초 카메라 권한 요청이다.
  이전 마이크 헬퍼도 권한 요청 시 활성화와 숨김을 사용했다.
- 재생 중 게임 포커스를 잃거나 UnityModManager 창이 열려 있으면 네이티브 입력을
  해제하고 그 구간을 건너뛴다. 게임 판정 재생과 입력 표시의 경로는 분리되어 있다.
- 기존 펌프 요약의 전송 개수만으로 운영체제와 키뷰어가 실제 입력을 수신했는지는
  확인할 수 없다.

## 이번 변경

`TUFReplay/Replay/NativeInput/ReplayNativeInputPlayer.cs`에서 입력 허용 상태나 차단
사유가 바뀔 때만 로그를 남긴다. 프레임마다 같은 로그를 반복하지 않는다. 포커스
판정과 입력 전송 동작은 기존대로 유지한다.

로그에는 다음 정보가 들어간다.

- `Focus ready` 또는 `Focus blocked`
- `application_not_focused`, `umm_window_open_or_stabilizing`, `focus_stabilizing`
  등의 차단 사유
- 실제 전송기 이름: 일반 재생의 `MacOsNativeInputEmitter`와 캘리브레이션의
  `NullNativeInputEmitter` 등을 구별할 수 있다.
- 기존 포커스 검사기의 상태 설명

예를 들어 `Focus blocked`와 `application_not_focused`가 눌림 표시가 사라지는 시점에
나오면 게임 포커스로 입력이 차단된 것이다. `Focus ready`인 상태에서 문제가 계속되면
포커스 검사 외의 입력 전달 경로를 확인해야 한다.

## 검증

- `./scripts/run.sh mod-check`: 통과. macOS 헬퍼 자체 검사, 네이티브 입력 코어 검사,
  C# 빌드, Unity/Mono 호환성 검사, C# 테스트를 수행했다. 기존 포커스 손실·복귀와
  일시정지·재개 테스트가 포함된다. `--no-install` 경로로 실행했다.
- `./scripts/run.sh mod-format check`: 변경된 C# 58개 파일 검사 통과.
- 실제 게임에서의 눌림 표시와 포커스 전환 재현: 미확인.

진단을 게임에 반영하려면 이 전용 워크트리에서 `./scripts/run.sh build`를 실행해야
한다. 문제 재현 시점의 새 `Player.log`로 포커스 차단 여부를 확인할 수 있다.
