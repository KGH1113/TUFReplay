# 카메라 기능 수정 및 검증

작업 위치: `/Users/kgh/dev/src/tuf-replay-webcam`  
브랜치: `feat/webcam-recording` (`dev` 기반)

## 변경한 동작

- 카메라를 켜면 게임이 열려 있는 동안 캡처 세션을 유지한다. 플레이를 시작하거나 끝낼 때 카메라를 다시 열지 않고 영상 저장만 시작하거나 끝낸다.
- macOS는 AVFoundation 세션과 AVAssetWriter를 사용한다. Windows는 계속 실행되는 DirectShow 캡처와 플레이별 FFmpeg 인코더를 사용한다.
- 실시간 미리보기는 960×720 범위에서 원본 비율을 유지하며 최대 30fps로 공유한다. 16:9 카메라는 960×540으로 표시된다. 고정 크기 버퍼에는 실제 프레임 크기와 최신 프레임만 들어가며, 화면에 표시할 때만 Unity 텍스처를 갱신한다.
- 게임 실행 후 첫 커스텀 레벨 플레이 전에 uGUI 카메라 확인 모달을 표시한다. 카메라를 켠 상태에서는 첫 영상 프레임을 받은 후 시작할 수 있다. 카메라 없이 시작하거나, 에디터에서 뒤로 돌아갈 수도 있다.
- 일반 플레이의 실시간 표시와 리플레이의 녹화 영상 표시는 각각 설정할 수 있다.
- 카메라를 웹 미리보기 또는 게임 화면에서 직접 드래그할 수 있다. 화면 밖 배치를 허용하며 드래그 종료 시 위치를 저장한다. 게임에서는 오른쪽 아래 손잡이로 크기도 바꿀 수 있다.
- 프리셋은 Compact / 용량 절약, Balanced / 균형, Quality / 품질이다. Quality는 1080p, 30fps, 3Mbps를 목표로 한다.
- 웹 모달을 두 열로 배치하고, 선택한 프리셋에 테두리와 체크 표시를 추가했다. 저장 한도와 보관 기간 설명, 작은 카메라 새로고침 아이콘, 접을 수 있는 싱크 보정을 제공한다.
- UI의 명칭을 Camera / 카메라로 통일하고 Preparing camera 표시와 가로·세로 위치 슬라이더를 제거했다.

## 실제 기기에서 확인할 항목

게임을 실행한 상태에서 실제 카메라의 OS 권한 요청, 여러 플레이 사이의 카메라 표시등 유지, 실시간 영상과 녹화 영상의 재생을 아직 확인하지 않았다. Windows의 DirectShow 장치 캡처도 이 macOS 환경에서는 실행하지 않았다. 실제 게임에서 모달의 첫 플레이 차단, 드래그 입력 처리, 영상 싱크를 확인할 필요가 있다.

위 테스트는 모드 설치를 변경하지 않는 검증 모드로 실행했다. 게임에 적용할 때는 이 작업 폴더에서 `./scripts/run.sh build`를 실행하고, 웹 개발 화면은 `bun run web:dev`로 실행한다. UI 번들은 이미 생성했으며, 모달의 배치를 다시 바꿀 때는 Unity의 **Tools → TUFReplay → Build Runtime UI Bundles** 메뉴로 갱신한다.

커밋과 푸시는 하지 않았다. 기존 `tuf-replay-dev` 워크트리는 수정하지 않았다.

## 후속 수정: FPS, 상하 방향, 원본 비율

- 미리보기의 10fps 제한을 최대 30fps로 올렸다. macOS는 시작 시각에 고정된 프레임 간격을 사용해 콜백 시간이 조금 흔들려도 갱신 속도가 계속 낮아지지 않게 한다. 용량 절약 프리셋도 30fps를 요청하며 비트레이트는 600kbps로 유지한다.
- macOS 미리보기를 Unity의 아래쪽 행부터 시작하는 픽셀 순서에 맞췄다. 위·아래와 왼쪽·오른쪽의 색이 다른 합성 프레임으로 방향을 검증했다. 녹화 원본과 사용자의 좌우 반전 설정은 각각 기존 역할을 유지한다.
- macOS는 해상도 프리셋에 카메라 비율을 맞추지 않고 기기 포맷에서 원본 비율을 유지한다. 녹화 크기는 품질별 최대 크기 안에서 균등 축소한다. Windows도 고정 크기의 패딩을 제거하고 FFmpeg가 출력한 실제 크기를 미리보기와 인코더에 전달한다.
- 16:9 카메라는 용량 절약에서 640×360, 4:3 카메라는 균형에서 960×720으로 저장된다. 작은 원본을 확대하지 않는다. H.264/YUV420에 필요한 짝수 크기로 맞추면서 생기는 2픽셀 미만의 반올림 차이는 허용한다.
- 공유 미리보기는 원본 비율에 맞는 실제 크기를 헤더로 전달한다. Unity는 크기가 바뀔 때만 텍스처와 픽셀 배열을 다시 만든다. 당시 고정 버퍼의 최대 크기는 307,264바이트였으며, 아래 화질 개선에서 상한을 높였다.

수정 후 `./scripts/run.sh mac-helper`, `./scripts/run.sh mod-check`, `./scripts/run.sh web-check`를 다시 실행해 통과했다. 웹 테스트는 124개였다. C# 검증에는 비율 유지, 확대 방지, 프레임 크기 변경, 잘못된 메타데이터 거부 및 고정 메모리 크기를 추가했다. macOS 검증에는 30fps 콜백의 ±2ms 시간 흔들림과 세로 프레임을 추가했다. 실제 카메라와 Windows DirectShow 장치에서의 검증은 아직 하지 않았다.

적용할 때는 이 워크트리에서 `./scripts/run.sh build`를 실행한 뒤 게임을 다시 시작한다. macOS 헬퍼도 함께 바뀌었으므로 모드 DLL만 교체하면 이번 수정이 전부 적용되지 않는다. 웹 개발 화면은 `bun run web:dev`로 실행한다.

## 후속 수정: 미리보기 깜빡임과 화질

깜빡임의 원인은 프레임을 쓰는 동안 공유 버퍼가 일시적으로 읽기 불가능해지면 미리보기 자체를 숨기는 처리였다. 첫 정상 프레임을 받은 뒤에는 준비 상태를 유지하며, 게임 화면은 마지막으로 업로드한 텍스처를 계속 표시한다. 카메라 크기가 바뀔 때도 새 프레임을 완전히 복사하고 업로드한 다음 텍스처를 교체하므로 빈 텍스처가 중간에 표시되지 않는다. 복사한 프레임의 크기도 함께 반환해 픽셀과 비율 정보가 다른 프레임에서 섞이지 않도록 했다.

기존 미리보기에는 H.264 압축을 적용하지 않았지만, 최대 320×240 제한 때문에 크게 표시하면 흐리고 Windows의 단순 픽셀 샘플링으로 작은 무늬가 깨질 수 있었다. 최대 크기를 960×720으로 높이고 원본 비율을 유지한다. 16:9 영상은 320×180에서 960×540으로 바뀌어 픽셀 수가 9배가 된다. 작은 카메라 원본을 확대하지는 않는다.

macOS는 [Core Image의 Lanczos 축소 필터](https://developer.apple.com/documentation/coreimage/cilanczosscaletransform)를 적용한다. 재사용하는 내부 버퍼에서 렌더링한 뒤 공유 버퍼에 빠르게 복사하므로, 렌더링 내내 읽기를 막지 않는다. Windows는 미리보기에 영역 평균 축소와 색차 채널의 보간을 적용하고 계산 계수를 재사용한다. FFmpeg의 캡처 및 녹화 축소에는 [Lanczos 스케일링](https://ffmpeg.org/ffmpeg-scaler.html)을 사용한다. 모든 변환은 게임 스레드 밖에서 처리한다.

해상도 외에 녹화에는 아래 처리를 적용하고 있다. 미리보기에는 녹화용 손실 압축을 적용하지 않는다.

| 녹화 프리셋 | 최대 크기 | FPS | H.264 목표 비트레이트 | 예상 용량 |
| --- | --- | --- | --- | --- |
| 용량 절약 | 640×480 | 30 | 0.6Mbps | 약 4.5MB/분 |
| 균형 | 1280×720 | 30 | 1.2Mbps | 약 9MB/분 |
| 품질 | 1920×1080 | 30 | 3Mbps | 약 22.5MB/분 |

저장 영상의 실제 크기는 위 범위 안에서 카메라 비율에 맞춰 축소한다. 비트레이트가 낮은 용량 절약에서는 녹화 영상의 작은 무늬나 빠른 움직임이 흐려질 수 있다. 새 미리보기는 녹화 프리셋과 별도로 필요한 캡처 해상도를 유지하고, 인코더가 선택한 프리셋의 저장 크기로 축소한다. 이번 수정에서 녹화 비트레이트와 저장 한도는 바꾸지 않았다.

공유 버퍼는 최대 2,764,864바이트(약 2.64MiB)로 고정되고 최신 프레임만 덮어쓴다. macOS의 렌더링용 버퍼와 Unity의 픽셀 배열·텍스처도 크기가 같을 때 재사용한다. 미리보기 메모리와 처리량은 증가하지만, 녹화 파일 용량은 증가하지 않는다.

수정 후 `./scripts/run.sh mod-format`, `./scripts/run.sh mod-check`를 실행해 통과했다. macOS Apple silicon/Intel 헬퍼 빌드와 self-test, 모드 및 Mono 호환성, C#·업데이트 검증이 통과했다. 새 회귀 검증은 쓰기 도중 마지막 프레임 유지, 완료 전 첫 프레임 거부, 크기 변경 시 픽셀과 크기의 일치, 고정 메모리 상한, 미세한 체크무늬 축소 및 Windows 변환의 프레임별 할당 없음까지 확인한다. macOS 합성 프레임에서는 더 높은 미리보기 해상도, 상하 방향, 가로·세로 비율, 30fps 갱신 및 체크무늬 축소를 확인했고, 미리보기 원본보다 낮은 640×360 녹화의 H.264 인코딩·디코딩도 통과했다. 이번에는 웹 코드를 바꾸지 않아 웹 검증은 앞선 124개 통과 결과를 유지한다.

실제 카메라와 게임 화면에서의 화질·갱신 속도는 아직 검증하지 않았다. 적용은 `/Users/kgh/dev/src/tuf-replay-webcam`에서 `./scripts/run.sh build` 후 게임 재시작으로 진행한다. 헬퍼와 모드가 함께 업데이트되어야 한다.

## 후속 수정: Discord 미리보기와 색감 차이

같은 구도에서 촬영한 두 스크린샷에서 TUFReplay 쪽의 검은 매트와 회색 키캡이 더 밝고 대비가 낮아 보였다. 낮은 해상도는 글자와 윤곽이 흐린 현상은 설명하지만, 넓은 단색 면의 밝기와 색이 바뀌는 현상을 모두 설명하지는 않는다.

macOS의 실제 캡처 형식인 NV12에 Rec.709 색 행렬·전달함수 메타데이터를 붙인 합성 영상으로 현재 변환 경로를 재현했다. 밝기 성분 128은 영상 범위를 RGB로 변환하면 약 130이어야 하지만, 기존 Core Image 색 관리 경로에서는 142가 됐다. 밝기 성분 64는 약 56 대신 64로 나왔다. 검정과 흰색은 그대로이고 중간 밝기가 올라가는 이 동작은 해상도와 무관하다. RGB 합성 프레임의 0~255 회색은 기존 경로에서도 보존되어, 기존의 RGB 원색·방향 검증만으로는 이 문제를 발견할 수 없었다.

Core Image의 작업 색공간을 `NSNull`로 설정하고 렌더링의 출력 색공간도 `nil`로 지정했다. NV12의 영상 범위와 YCbCr 행렬 변환은 유지하면서, 카메라의 비선형 영상 값을 다시 sRGB로 감마 변환하지 않도록 했다. 임의의 밝기·채도 보정은 넣지 않았다. 이 동작은 [Apple의 workingColorSpace 설명](https://developer.apple.com/documentation/coreimage/cicontextoption/workingcolorspace)의 색 관리 비활성화 경로를 따른다. 녹화 인코더는 이 미리보기 RGB 변환을 사용하지 않는다.

`./scripts/run.sh mod-check`를 다시 실행해 통과했다. macOS self-test에 실제 캡처 형식의 검정·회색·흰색과 빨강·초록·파랑을 추가해 명암 범위, 감마, Rec.709 색 행렬과 불투명도를 검증했다. 합성 영상의 색 값은 정상화됐지만, Discord의 내부 처리나 두 앱의 자동 노출·화이트밸런스 설정까지 동일함을 확인한 것은 아니다. 실제 카메라 화면의 최종 비교는 새 헬퍼를 적용한 뒤 확인해야 한다.
