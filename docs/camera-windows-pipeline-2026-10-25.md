# Windows 카메라 캡처·인코딩 개선

## 변경 목적

Windows 고화질 녹화에서 CPU 인코딩, 프레임 복사, 미리보기 변환이 동시에 쌓이고 짧은 지연만으로 전체 영상을 버리던 경로를 변경했다. 게임 입력 기록과 카메라의 실제 촬영 시각을 유지하는 것이 우선이다.

## 구현

- DirectShow 지원 모드를 열거해 해상도·픽셀 형식·프레임률을 명시적으로 선택한다. 1080p60이 없는 장치는 1080p30 등 지원 모드를 사용할 수 있다. 분수 프레임률을 유지하고 동등한 모드에서는 USB 대역폭을 줄이는 MJPEG를 우선한다. 광고된 모드가 실패하면 제한된 횟수만 재시도하고 마지막에는 장치 기본 설정을 사용한다.
- NVIDIA NVENC → Intel Quick Sync → AMD AMF → 소프트웨어 순서로 실제 테스트 프레임을 인코딩한다. 설치된 FFmpeg의 코덱 목록만으로 GPU 사용 가능 여부를 판단하지 않는다. 선택 결과는 실행 파일·프로필별로 캐시하고 인코더 실패 시 무효화한다.
- 인코더 설정은 B-frame·lookahead를 사용하지 않는다. CPU 대체 경로는 `libx264 ultrafast`, 2개 스레드를 사용한다. 준비 이후 GPU 인코더가 실패하면 건강한 카메라 세션을 유지하며 다음 녹화는 CPU로 전환한다. 이미 실패한 녹화 전체를 다른 인코더로 재인코딩하는 기능은 아니다.
- 카메라를 준비할 때 YUV 프레임 8개를 할당한다. 1080p 기준 프레임 메모리는 약 24.9 MB이며, 녹화 중 프레임 버퍼를 추가 할당하지 않는다. 캡처·최신 프레임·녹화·미리보기는 참조를 공유하고 마지막 사용자가 반환한 뒤에만 재사용한다.
- 녹화 대기열은 3프레임으로 제한한다. 밀리면 대기 중인 오래된 프레임을 교체한다. 이미 인코딩 중인 버퍼를 덮어쓰거나 캡처를 대기시키지 않는다.
- 프레임의 원래 캡처 시각을 Matroska/I420 스트림에 싣고 VFR H.264 MP4로 인코딩한다. 누락 구간을 시간축에서 제거하지 않으므로, 처리하지 못한 프레임 때문에 영상 재생 속도가 빨라지지 않는다. 첫 저장 프레임의 실제 시각을 입력 리플레이 동기화 기준으로 기록한다.
- 녹화 해상도로 캡처 단계에서 한 번만 축소한다. Compact에서 미리보기 때문에 더 큰 영상을 캡처한 뒤 다시 축소하던 경로를 제거했다. 이미 목표 FPS 이내인 협상된 모드에는 프레임 제한 필터를 걸지 않는다.
- 미리보기 색 변환은 독립된 작업 스레드에서 최대 30fps, 대기 프레임 1개로 처리한다. 공유 화면 버퍼가 사용 중이어도 캡처 스레드를 막지 않는다. Mono의 `WriteArray<byte>`를 포인터 기반 `Marshal.Copy`로 교체했다.
- 장치 모드 재시도는 이전 캡처 프로세스의 종료를 확인한 뒤 진행한다. 준비 실패 시 카메라와 대기 녹화 작업을 정리한다.
- Windows 캡처·인코더 프로세스와 미리보기 작업의 CPU 우선순위를 낮춰 게임 작업이 먼저 실행되도록 한다.
- 실제 인코더 프로세스는 첫 프레임을 받은 백그라운드 작업에서 시작한다. 이때 해당 런의 파일 크기 제한을 `-fs`에 적용하며, 대기 중인 빈 녹화 작업은 GPU 인코더 세션을 점유하지 않는다.
- 크기 제한에 도달한 영상의 길이는 FFmpeg 진행률 대신 완성된 MP4의 비디오 트랙에서 읽는다. 파일 내용을 메모리에 올리지 않고 필요한 헤더만 탐색한다. 크기 제한 때문에 입력 파이프가 닫혀도 MP4 마무리 후 종료 상태를 확인해 정상 저장과 실패를 구분한다.
- `[Webcam]` 로그에 선택한 장치 모드·인코더, 인코더 검사 실패 이유, 인코딩 프레임 수·교체한 프레임 수를 기록한다.

원시 프레임을 두 FFmpeg 프로세스 사이에서 CPU 메모리와 파이프로 전달하는 부분은 남아 있다. 전체 캡처를 GPU 메모리 안에서 처리하는 구조로 바뀐 것은 아니다.

## 검증

`./scripts/run.sh mod-check`에서 C# 빌드, Unity/Mono 호환성 검사와 전체 C# 테스트를 검증한다. 추가한 주요 회귀 검사는 다음과 같다.

- 실제 FFmpeg로 기록한 MP4에서 의도적인 97프레임 교체 후에도 `0, 1.96, 1.98, 2.00`초 타임스탬프가 그대로 남는지 확인한다.
- 준비 시 32 MiB였던 제한을 런 연결 시 2 MiB로 바꾼 뒤 실제 파일이 제한 안에서 보존되는지, `SizeLimited`가 설정되는지, 메타데이터 길이가 마지막 저장 패킷과 일치하는지 확인한다.
- 빈 녹화 준비·취소·첫 입력 이전 프레임 제외·프레임 버퍼 반환·미리보기 공유 버퍼 경합을 확인한다.
- 장치 모드 선택·하드웨어 사용 불가 시 대체 선택·선택 캐시·MP4 헤더의 32/64비트 경계와 잘못된 구조를 확인한다.

최종 검증 결과: `./scripts/run.sh mod-check` 통과. C# 빌드 경고·오류 0개, Unity/Mono 호환성 검사와 전체 C# 테스트 통과. `./scripts/run.sh mod-format check` 및 `git diff --check`도 통과했다. 위 과부하·실제 파일 제한 테스트는 설치된 FFmpeg를 실행해 검증했다. Windows 웹캠과 GPU를 사용한 실기기 검증은 아래 범위로 남아 있다.

`./scripts/run.sh camera-copy-bench 100` 결과: macOS의 독립 Mono 6.13.0, 워밍업 10프레임, 경로별 100회. 쓰기 전후 바이트 동일성도 검사했다.

| RGBA 프레임 | 기존 WriteArray 평균 / p95 | 일괄 쓰기 평균 / p95 |
| --- | --- | --- |
| 960 × 540 | 7.956 / 8.902 ms | 0.037 / 0.059 ms |
| 960 × 720 | 10.716 / 11.972 ms | 0.057 / 0.111 ms |

위 수치는 메모리 복사만 측정한 결과다. Windows 게임 내 FPS, RTX 4060 인코딩 속도, 사용자의 웹캠 USB 전송 성능을 측정한 수치는 아니다.

## Windows 실기기 확인 범위

이 작업 환경은 macOS이므로 실제 DirectShow 웹캠 및 NVENC/QSV/AMF 실행은 검증하지 못했다. Windows에서는 다음을 확인한다.

1. 고화질 활성화 후 로그의 `Camera capture mode`와 `Camera encoder selected: h264_nvenc`를 확인한다. 실패한 GPU 검사는 같은 로그에 이유가 남는다.
2. 30fps 전용 웹캠의 고화질 준비, 60fps 지원 웹캠의 고화질 녹화, 카메라 재연결을 확인한다.
3. 미리보기 표시/숨김, 빠른 재시작, 긴 녹화, 파일 크기 제한 도달을 확인한다.
4. 저장된 영상을 리플레이에서 재생·일시정지·탐색해 입력과의 동기화를 확인한다. 강제 부하 시 영상의 순간 정지는 허용하지만 누적 시간축 이동은 없어야 한다.

## 구현 근거

- [FFmpeg DirectShow 입력 구현](https://github.com/FFmpeg/FFmpeg/blob/master/libavdevice/dshow.c): 지원 모드 목록과 100ns 단위 프레임 간격.
- [Matroska V_MS/VFW/FOURCC](https://www.matroska.org/technical/codec_specs.html#v-ms-vfw-fourcc): I420 BITMAPINFOHEADER.
- [Matroska 요소 정의](https://www.matroska.org/technical/elements.html): TimestampScale과 클러스터 타임스탬프.
- [FFmpeg NVENC 구현](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/nvenc.c), [QSV 구현](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/qsvenc.c), [AMF 구현](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/amfenc.c): 하드웨어 입력 형식과 타임스탬프 처리.
